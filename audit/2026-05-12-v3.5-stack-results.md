## Why each wave probably regressed (debugging hypotheses)

These are FALSIFIABLE hypotheses for next-session work, not committed
explanations — the actual root causes need replay-level digging.

### opening (40.6%)

Likely causes:
- Pure-value denominator `(d + 1)` (no ship-cost) makes the proposer
  prefer the highest-production neutral globally, even if FAR — at
  step 0 a 60-unit launch arrives at step 60 by which time the same
  source could have fed 5 closer captures.
- 1 proposal per (source × neutral) means a 4-home × 8-neutral = 32
  proposals at step 0; settle_plan's per-source greedy picks at most
  4 (one per source). But the highest-scoring 4 may all converge on
  the same FAR-but-high-prod neutral. The arrival ledger blocks
  duplicates, but only AFTER one source has committed — the others
  fall back to their next-best, which is still likely a far target.

Debug for next session:
- Replace pure-value denominator with `(0.5 * base_ships + d + 1)` so
  the scorer respects ship-cost too.
- Cap target distance per source to ~30 units (the nearest 4-6
  neutrals) so the opening doesn't reach across the board.
- Run replay diff vs frozen — confirm the opening Mission actually
  fires at step 0 with the right target IDs.

### drain (46.9%)

Likely causes:
- `MIN_DRAIN_SHIPS=30` triggers in mid-game when sources hit 30+
  ships. By that point those sources are the strongest defenders;
  flushing them strands the home cluster.
- `incoming_enemy_eta` only sees fleets currently in flight; it
  doesn't see "an enemy will launch next turn." Even a planet with
  no inbound enemy this turn can be threatened by next turn's launch.

Debug:
- Raise `MIN_DRAIN_SHIPS` to 60 (only flush sources that are clearly
  over-stocked).
- Add a "no drain within 20 turns of opening" guard.
- Require `enemy_eta > our_eta + 15` (not 5) so drain only fires
  with substantial safety margin.

### gang_up (50.0%)

Likely cause:
- Pairs' natural ETAs differ by 0-3 turns. Env's combat resolver
  groups at integer steps; a 3-turn gap means the lead fleet arrives
  3 turns earlier, fights alone, and the follow-up fights the
  reinforced defender. **Same-step arrival doesn't happen by default;
  it requires the slower source to delay launch**, which I did NOT
  implement.

Debug:
- Require `eta_gap = 0` (or 1) only.
- Or: add explicit launch-delay logic — the slower source emits an
  Intent that the env will defer to a future turn (which the env
  doesn't natively support — would need a per-agent state shim
  remembering "launch this Intent at step X").

### recapture (53.1%)

Likely cause (closest to neutral, smallest issue):
- `RECAPTURE_BONUS_PEAK=1.5` competes with high-scoring snipe targets.
  When recapture wins out, we send a fleet at the recently-lost
  planet, but the enemy has already started fortifying — the bounce
  rate on recapture targets is plausibly higher than the bounce rate
  on snipe targets.

Debug:
- Lower bonus to `RECAPTURE_BONUS_PEAK=1.2`.
- Add a "target.ships < 15" gate so recapture only fires when the
  new owner hasn't yet fortified.
- Or: gate recapture on `world_model.ships_at(target, eta) < N` — use
  the predictive model, not the current snapshot.

## What we learned (epistemics)

1. **The top-10 fingerprint analysis is qualitatively right.** Top-10
   IS more aggressive, opens earlier, empties sources more, etc. The
   gaps are real, measured across 50 replays.
2. **Translating fingerprints to scoring rules is the hard part.**
   Behavioural features (mean_garrison_at_launch=11) don't directly
   convert into a single threshold (MIN_DRAIN_SHIPS=30). Top-10 likely
   has many interacting context-aware gates we haven't replicated.
3. **The per-source greedy planner is more sensitive than expected.**
   Adding ONE new Mission class (opening) drops winrate 9pp. Mission
   class additions are NOT independent; they interact through the
   settle_plan ledger.
4. **The v3.4 NEUTRAL_BONUS lesson generalises**: any change that
   shifts a lot of mass in the proposal-score distribution likely
   regresses on first try. Adjustments need to be conditional and
   narrow.

## Recommendation

**Do NOT submit v3.5.** v3_snipe at μ=1055 stays the rolling-last-2
floor (with v2 at μ=974 as the speculative-eviction casualty when a
future v3.6 ships).
